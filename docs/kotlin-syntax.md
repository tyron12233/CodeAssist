# kotlin-syntax (experimental)

The Kotlin compiler's own multiplatform parser, vendored and built for iOS, with a parity suite that checks it
against the PSI parser this IDE actually ships. Nothing depends on it.

## What changed, and why it matters

This module started as a hand-written port of the compiler's grammar. It should not have: Kotlin master
already contains `compiler/multiplatform-parsing`, ~11,000 lines of `commonMain` Kotlin holding the JFlex
lexer emitted as Kotlin, `KtTokens`, `KtNodeTypes`, `KotlinParsing`, `KotlinExpressionParsing`, the
whitespace binders and a `LightSyntaxTree`. It is Apache 2.0, and its only real dependency,
`org.jetbrains:syntax-api`, publishes `iosArm64` and `iosSimulatorArm64`.

Upstream builds that module for `jvm` and `wasmJs` only. **It compiles for both Apple targets unchanged.**
That is the headline: the grammar problem is solved by the Kotlin team, kept in step with the compiler by
definition, and it reaches iOS today.

So the parser here IS the compiler's grammar rather than a reimplementation of it, and "100% syntax parity"
stops being a goal to grind toward and becomes a property to verify.

## Layout

```
src/commonMain/vendor/      the Kotlin compiler's parser, byte-identical — 10,216 lines, see vendor/VENDOR.md
src/commonMain/kotlin/      ours — 1,971 lines: KotlinSyntax (the entry point) and the Kt* facade
testData/kotlin-psi/        Kotlin's compiler/psi/psi-impl/testData, .kt and .kts only (774 files)
baselines/parser-parity.txt the divergences that remain, tracked so they can only shrink
```

Multiplatform (jvm + iosSimulatorArm64 + iosArm64). The vendored sources keep their upstream package names so
a re-sync is an overwrite rather than a merge.

The hand-written lexer and parser this module started with are **gone**. What survived is the part that was
always the real work: the `Kt*` facade, now reading a `LightSyntaxTree` instead of its own tree.

## The parity suite

`KotlinParserParityTest` parses all 774 corpus files with the vendored grammar and with the PSI parser from
`:kotlin-compiler-deps`, renders both trees, and diffs them.

**Expectations come from our pinned compiler, not from the corpus's golden `.txt` dumps.** Those were
generated by whatever Kotlin revision committed them while this build pins `2.4.20-dev-6138`, so comparing
against them would report version skew as parser error. The `.txt` files are therefore not vendored at all.

**Currently 719/774 (92.89%)** on that corpus, and **2381/2381 on this repository's own Kotlin sources** —
the second suite is the other half of the question, since the compiler's corpus is adversarial by design
while the repo is the ordinary code the parser will actually be asked to read. The residue is in `baselines/parser-parity.txt`, which may only shrink: a file
that diverges without being listed fails the suite, and a listed file that starts agreeing also fails. That is
what keeps the number honest.

Getting from 0% to 92.89% was almost entirely about learning what is NOT a parser difference, and each of
those is now a documented rule in the comparison rather than a fudge:

- The multiplatform vocabulary RENAMED some kinds. PSI's `FUN_KEYWORD` is `FUN_MODIFIER` there. Names are
  paired by field name and then by token text, since a rename looks exactly like two unrelated kinds.
- `marker.collapse(type)` produces a LEAF in PSI but a composite wrapping its tokens in the light tree. Every
  modifier keyword goes through it, and so do the operators the new lexer leaves in pieces: `!!` is
  `(EXCLEXCL EXCL EXCL)` here and one token to PSI.
- PSI parses blocks and lambdas lazily, which shows up as a tree difference on erroneous input that is not
  one. The comparison forces a full parse first.
- An empty PSI composite has no children, like a token does. Rendering it as a token made every file in the
  corpus look like a divergence.

What is left is genuine old-parser-versus-new-parser behaviour, mostly `BAD_CHARACTER`: the two lexers
disagree about exotic whitespace and about what belongs inside an error element.

## The facade, which is the part that is ours

The vendored parser produces a `LightSyntaxTree`, not PSI, so the `Kt*` facade over it is the actual mapping
cost — the 130 types and ~3,000 references the editor backend already speaks. Two things about the tree shape
through:

- **An element is `(session, node)`, never a node alone.** `LightNode` is a value class around an `Int` index
  into flat arrays; it does not know its tree, and there is nowhere to hang a wrapper. `KtTreeSession` holds
  the tree and caches one wrapper per index, which is not a performance flourish: the analysis engine keys
  identity maps on elements, and a facade minting a fresh wrapper per access would turn each of those into a
  leak that still passed its own tests.
- **Doc comments live INSIDE the declaration they document.** The compiler's comment binders put them there.
  The hand-written parser had no binders, so the facade used to look backwards at siblings; it now looks in,
  and falls back to looking out.

## The port probe: does the editor backend's code actually run on this?

`src/commonTest/.../port/KotlinControlFlow.kt` is a **verbatim copy** of `:lang-kotlin`'s
`resolve/KotlinControlFlow.kt` — 443 lines of real control-flow analysis, 26 PSI imports, no other coupling —
with its imports rewritten and nothing else touched. `PortProbeTest` runs it.

The whole diff against the original is **27 import lines, the package line, and 6 body lines**, and those six
are all one rename: `PsiElement` to `KtElement`. Nothing else changed, and the analysis produces correct
answers: dead code after `return`/`throw`/`break`, locals read before assignment, `lateinit` correctly
exempt, and — the direction that matters — no false positives after a *conditional* return.

It runs on the iOS simulator as well as the JVM. That is `:lang-kotlin`'s own code executing off the JVM,
which is the thing this module exists to find out.

Getting there closed four real gaps, each found by the compiler rather than guessed at:

- **`KtLoopExpression` was missing.** The backend walks loops through that base, not the three concrete types.
- **`hasInitializer()`, `hasDelegate()`, `hasValOrVar()`, `hasBlockBody()`, `hasDefaultValue()` must be
  FUNCTIONS.** `hasX()` is not a Java getter pattern, so Kotlin sees a method and every call site writes the
  parentheses. 120+ of them in `:lang-kotlin`.
- **`isX()` is the opposite.** It IS a getter pattern, so Kotlin sees a synthetic property and call sites
  write `.isElse`, not `.isElse()`. Properties, therefore. Getting this backwards broke everything twice.
- **`getReferencedName()`, `getArgumentExpression()`, `getArgumentName()`, `getSpreadElement()`,
  `getLabelName()` must be functions too** — 207 of `:lang-kotlin`'s ~226 Java-style getter calls are those
  five. A Kotlin property compiles to the same JVM getter but cannot be *called* that way from Kotlin source.

And `KtTokensCompat.kt` exists because the vendored vocabulary renamed every modifier — `PRIVATE_MODIFIER`
where PSI said `PRIVATE_KEYWORD`, 34 of them, 82 references in `:lang-kotlin`. It re-exports all 163 tokens
and token sets under PSI's names, so the migration is an import swap rather than 82 hand edits.

## Measured

`KotlinParserBenchmarkTest`, over the twelve largest Kotlin files in this repository (33,877 lines, 2.0 MB of
real code), on a desktop JVM with a warm JIT:

| | |
|---|---|
| Vendored parser | 33,528 chars/ms |
| PSI parser | 14,576 chars/ms |
| | **vendored is 2.3x faster** |

That is a reason to want this parser on the JVM for its own sake, independent of portability.

**But a full parse does NOT make incremental reparse redundant, which is the answer I was hoping against.**
Latency by file size:

```
 1,482 lines   2.6 ms
 2,137 lines   1.5 ms
 3,653 lines   6.3 ms
 4,795 lines   6.8 ms   ← 81% of a 120Hz frame
```

Typical files are comfortable. The largest are not, and 6.8 ms is a floor twice over: it is the fastest of
twenty runs on a warmed JIT, and ART will be several times slower again.

The benchmark asserts a catastrophe bound rather than the frame, deliberately: asserting the frame would be
asserting this machine, it passes here at 81%, and it would flake on CI hardware.

## Incremental parsing

`IncrementalKotlinParse` closes that gap without an incremental mode, by using the split the grammar already
offers. In **lazy** mode the parser does not descend into function bodies: it counts braces past each one and
collapses it into a single `BLOCK`, exactly as PSI's lazy-parseable elements do. Bodies are most of a file, so
that alone is 2.1x. The interior of a body is then parsed only when asked for, and per keystroke that is one
body: the one under the caret.

There is a third level, and it is where the win actually is. Most keystrokes land inside a body and change
nothing outside it, so when that is provably true the file is **not reparsed at all** and the keystroke costs
one body rather than one file.

```
                      full parse   keystroke
 1,482 lines            7.1 ms      0.096 ms
 3,653 lines            6.6 ms      0.054 ms
 4,795 lines            7.0 ms      0.058 ms
                        -------------------
 totals                66.8 ms       0.54 ms   (124x cheaper)
```

Worst keystroke: **96 µs, or 1.2% of a 120 Hz frame**, down from 81%. Over that run, 280 edits were absorbed
without a file parse against 10 performed. Even if ART is ten times slower, that is about a millisecond.

The proof obligation for skipping the file parse is **brace balance**: typing `}` inside a body ends it early
and changes everything after it. So the edited body is re-lexed and checked to reach depth zero exactly at its
end and nowhere before. It LEXES rather than scanning characters, because a brace inside a string or a comment
is not a brace, and a scan would count it — there is a test for exactly that.

When the fast path applies the file tree is left stale and reparsed on first access, which is deliberate:
folding, breadcrumbs and the outline do not run per keystroke, so they can pay once. Reading `fileTree` inside
a typing loop gives back everything the fast path saves.

Two files are absent from that table. `IdeBackend.kt` and `LearnContent.kt` are declarations and string data
with no function body big enough to type in, so the benchmark skips them rather than measuring the slow path
and calling it the fast one.

### Two things that do not work, and cost time to discover

- **`withStartOffset` cannot select a sub-range.** It shifts the offsets of elements the parser MARKS, but not
  the tokens, which carry the offsets they were lexed at — and the builder still consumes from the first
  token. Used that way it silently parses the whole file and returns a tree whose composites are absolute and
  whose tokens are relative. `KotlinSyntax.parseBlock` therefore takes the block's own text and returns
  RELATIVE offsets, and `ExpandedBlock` carries the translation explicitly.
- **A collapsed block is not childless.** It keeps every token it swallowed and loses only the structure, so
  "has no composite children" is the test for whether a body still needs expanding. Testing for no children at
  all finds nothing.

### What is cached

An expanded body is kept against its start offset and validated against its text, so typing in one body keeps
every body above the caret and drops those below it. Caching on text alone would be wrong: a body's tree
carries offsets, so the same body moved down a line is a different answer.

## Not done yet

- Nothing in `:lang-kotlin` actually depends on this; the probe is a copy, not a wiring. The remaining known
  cost for a real migration is the `.isX()` call sites that need their parentheses removed, which the
  compiler finds for you.
- KDoc parsing is vendored but unexercised.
- The 55 baselined divergences are unexamined individually; they are known to be dominated by `BAD_CHARACTER`
  handling, but nobody has read them one at a time.

## Why any of this exists

The editor backend (`:lang-kotlin`) uses the Kotlin compiler for exactly one thing: parsing. It then walks the
resulting PSI directly — 130 distinct `Kt*` types over ~3,000 references — and does its own symbols,
inference, completion and diagnostics on top.

That parse is the single thing in the language stack with no Kotlin/Native path, so it is what pins Kotlin
completion and error checking to the JVM. Measured on the current tree:

| | lines |
|---|---|
| `:lang-kotlin` analysis code (excluding `interp/`, `compile/`) | 25,166 |
| of which deeply PSI-coupled (10+ references) | 18,274 |
| the neutral DOM those lines were meant to use | 81, and effectively unused |

Rewriting the grammar, or adopting a third-party one (tree-sitter, ANTLR), means owning a tree whose shape
differs from the one those 18,274 lines assume. Every divergence then surfaces as a wrong diagnostic under
correct code, which is the failure mode users punish hardest.

So this module mirrors the compiler's model instead. The compiler's own parser is a good target for that: its
`parsing` and `lexer` packages reference only **32 distinct IntelliJ types**, and five carry the weight —
`IElementType`, `TokenSet`, `PsiBuilder`, `WhitespacesAndCommentsBinder`, and the output tree. Reproduce those
and the grammar becomes a translation rather than a redesign.
